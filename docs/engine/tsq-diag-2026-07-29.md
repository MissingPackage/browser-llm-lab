# Diagnosi timestamp-query livello 2 — RISOLTO (2026-07-29, goal engine-fase-b1, fase 2)

## Sintomi (known-issue ereditato dalla fase A)

Su Chrome branded Linux/NVIDIA, con telemetria livello 2 attiva:
1. i timestamp GPU tornavano **azzerati** (gpuMs=null dichiarato);
2. il compute veniva **corrotto** (conformance 98.05% → 93.4%, maxΔlogit 5.8);
3. il microbench standalone con lo stesso pattern funzionava.

## Metodo

Matrice A/B a una variabile (`scripts/tsq-diag.mjs`, worker mode `tsqdiag`, knob
`opts.tsqDiag` in `createEngine`): 5 varianti × (64 token greedy deterministici +
logits finali) vs baseline `off`. Ipotesi: H1 = `timestampWrites` nel pass descriptor;
H2 = resolve/copy nello stesso encoder del forward; H3 = ring lungo (64).

## Risultati (results/engine/tsq-diag-4090-2026-07-29T20-54-*.json, pre-fix)

| variante | idsMatch | maxΔlogit | gpuMs |
|---|---|---|---|
| off | — | 0 | — |
| on-ring64-same (fase A) | ✗ | 22.49 | null |
| on-ring1-same | ✗ | 20.01 | null |
| on-ring1-own | ✔ | 0 | null |

H1 e H3 refutate; H2 confermata ma non completa: "own" curava la matematica, non gli
zeri. Il buffer etichettato ha chiuso il cerchio: Dawn riportava
`Buffer "tsq-staging" used in submit while mapped`.

## Root cause — bug NOSTRO della fase A, non del browser

In `flushTsq` la closure async chiamava `staging.mapAsync()` **sincronicamente
durante l'encoding**, cioè prima del `queue.submit()` contenente la copy verso quel
buffer. Dawn valida "buffer mapped usato in un submit" e **droppa l'intero command
buffer**:

- modo "same": il command buffer droppato conteneva anche il forward del token ⇒
  1 token ogni RING saltato interamente ⇒ corruzione a valle (98.05→93.4 = ~1/64);
- la copy verso lo staging non eseguiva mai ⇒ timestamp letti a zero;
- modo "own": veniva droppato solo l'encoder dedicato ⇒ matematica intatta, zeri
  persistenti — esattamente il pattern misurato;
- il microbench standalone attendeva il submit prima di mappare ⇒ funzionava.

## Fix (una variabile) e verifica

`flushTsq` ora **encoda soltanto** e ritorna lo staging; `armTsq` (la `mapAsync`)
parte **dopo** il submit. Verifica contro il repro originale:

- matrice post-fix (tsq-diag-4090-2026-07-29T20-55-*.json): tutte le varianti
  idsMatch=✔, maxΔlogit=0, **gpuMs ≈ 2.17-2.26 ms/token reali**, zero GPU error;
- conformance completa con `telemetryGpu:true` (`TSQ=1 node
  scripts/conformance-engine.mjs`): **GATE DOPPIO PASS** — 98.05% vs golden,
  100.00% vs cpuref-f64, identico alla fase A (conformance-4090-2026-07-29T20-56-*).
